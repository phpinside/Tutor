## 问题根因

`submit/route.ts:74` 用 `req.nextUrl.origin` 发起 HTTP 自调用触发处理。在阿里云 ECS + Nginx 反代环境下，`req.nextUrl.origin` 解析出的地址（通常是 `http://localhost:3000`）不可靠，自调用失败后被 `.catch(() => {})` 静默吞掉，记录永远卡在 `PENDING`（"等待处理"）。

你的服务器是长驻 Node 进程（非 serverless），**完全不需要绕一圈 HTTP 自调用**——直接在进程内调用分析函数即可，既可靠又省一次网络开销。

## 修复方案

### 1. 新建 `src/lib/planner-checker.ts` — 提取共享分析逻辑

将 `process/[id]/route.ts` 里的 `runAnalysis` 提取为独立函数 `runPlannerCheck(id, extractedText)`：
- 开头设置 `PROCESSING` 状态（带防重入：若已 PROCESSING/COMPLETED 则跳过）
- OpenAI 客户端加 `timeout: 120000`（2分钟）+ `maxRetries: 2`，防止 LLM 挂死
- 成功：`COMPLETED` + result
- 失败：打印日志 + `FAILED` + errorMsg（移除 `.catch(() => {})` 静默吞错）

### 2. 修改 `submit/route.ts` — 进程内直接调用

删除 73-79 行的 fire-and-forget self-fetch，替换为进程内异步调用：
```ts
void runPlannerCheck(record.id, extractedText).catch(err => {
  console.error('[planner-checker/submit] 触发分析失败:', err)
})
```
不再依赖任何外部 URL，彻底消除网络问题。

### 3. 修改 `process/[id]/route.ts` — 引用共享模块

- 删除内联的 `runAnalysis` 函数和手动 PROCESSING 更新
- 改为引用 `runPlannerCheck`（保留这个路由，作为"重试"入口）
- 路由守卫保留：仅跳过 PROCESSING/COMPLETED，PENDING/FAILED 可重试

### 4. 修改 `PlannerCheckerClient.tsx` — 添加"重试"按钮

- 为 `PENDING`（卡住超时）和 `FAILED` 的记录添加"重试"按钮
- 点击后 POST 到 `/api/tools/planner-checker/process/${id}`
- 现有 3s 轮询会自动捕获状态变化
